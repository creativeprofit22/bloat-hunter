### Capability 1: IPC Bridge 3-Way Sync

- **Entry**: `src/renderer/types/electron.d.ts` (type declarations)
- **Layers**: `src/preload/index.ts` (contextBridge) ↔ `src/main/ipc.ts` (handlers)
- **Destination**: Renderer hooks consume `window.electronAPI.*`

**Status: Channel names are fully synchronized across all three layers. No missing channels, no phantom handlers.**

**Gaps Found:**

| # | Where | What's Lost | Impact | Severity |
|---|-------|------------|--------|----------|
| 1 | `AdvisorPanel.tsx:32` → `ipc.ts:182` | `apiKey: ''` sent to `aiConfigure` despite main explicitly blacklisting it; `AISettings.tsx:61` correctly omits it | Interface contract violation — harmless now, fragile if validation tightened | Low |
| 2 | `electron.d.ts:72` + `preload:42` + `ipc.ts:196` → no renderer caller | `aiExplainItem` — full 3-layer chain wired, zero renderer callsites | Per-item AI explanation feature is dead-wired; unreachable from UI | Medium |
| 3 | `electron.d.ts:87` + `preload:23` + `ipc.ts:153` → no renderer caller | `isAdmin` — full 3-layer chain wired, never called before clean ops | No admin elevation check before destructive operations on system dirs | Medium |

**Details:**

**Gap 1 — `apiKey` field inconsistency:** `AdvisorPanel.tsx:32` sends `{ type, apiKey: '', baseUrl, model }` to `aiConfigure`. `AISettings.tsx:61` sends `{ type, baseUrl, model }` — no `apiKey`. Both reach the same handler at `ipc.ts:180-189`, which explicitly ignores any `apiKey` in the config and fetches it from secure storage instead (`ipc.ts:186`). The extra field is silently discarded. No runtime impact today, but the two call sites have divergent signatures for the same API — if validation is ever added to the config shape, one will break.

**Gap 2 — `aiExplainItem` dead-wired:** The `ai:explain-item` IPC channel is fully implemented: preload exposes it (`preload/index.ts:42`), main handles it (`ipc.ts:196-198`), and `advisor.explainItem()` (`advisor.ts:55-67`) builds a prompt and calls the AI provider. But no renderer component calls `window.electronAPI.aiExplainItem()`. The feature (per-file AI explanation) was built server-side but the UI surface was never connected.

**Gap 3 — `isAdmin` never called:** The `clean:is-admin` channel exists to check whether the app has admin privileges before attempting to delete system files (e.g., SoftwareDistribution). `useCleaner.ts:102` proceeds directly to `startClean` without checking. On Windows, deleting protected files fails silently with EACCES errors that show as per-item failures — no upfront warning.

### Capability 2: Scanner Config Propagation

- **Entry**: `useScanner.ts` (builds `ScannerConfig` from Zustand store)
- **Layers**: preload → ipc.ts → WorkerManager → worker thread → scanner-worker.ts
- **Destination**: Concrete scanner implementations (`BaseScanner.walkFiles`, per-scanner `scan()`)

**Status: Config object passes through all layers intact (WorkerManager sends full `workerData` without field-picking). All 8 ScannerType values are registered. But several config fields are silently ignored at the destination.**

**Gaps Found:**

| # | Where | What's Lost | Impact | Severity |
|---|-------|------------|--------|----------|
| 4 | `useScanner.ts:74,84` → no scanner reads it | `exclusions: string[]` collected from UI, never enforced in any scanner or `walkFiles` | User-configured exclusion patterns do absolutely nothing | **Critical** |
| 5 | `useScanner.ts:87` → `duplicates/scanner.ts:28` | `minSize=0` (no minimum) becomes `minSize=1` in DuplicatesScanner only; BigFilesScanner correctly uses `?? 0` | Zero-byte files excluded from duplicate detection; inconsistent cross-scanner | Low |
| 6 | `types.ts:73-80` → `big-files/scanner.ts:115-116` | `maxSize`, `includeExtensions`, `excludeExtensions` defined in type, scanner code handles them, but UI never populates them | Three filtering capabilities with working backend code but no UI controls | Medium |
| 7 | `useScanner.ts:84` → 4 of 8 scanners | `paths: string[]` ignored by `system-junk`, `browser-cache`, `app-leftovers`, `registry` scanners (they use hardcoded/rule-based paths) | User-configured scan paths silently have zero effect on half the scanner types | Medium |

**Details:**

**Gap 4 — `exclusions` completely inoperative (CRITICAL):** The user can add glob exclusion patterns in Settings (e.g., `node_modules`, `*.iso`). These are persisted, transmitted across IPC, arrive intact in the worker's `ScannerConfig` — and then silently do nothing. `BaseScanner.walkFiles` never checks `this.config.exclusions`. No scanner implementation reads the field. This is the single most impactful finding: an advertised, user-facing feature that is completely non-functional.

**Gap 7 — `paths` ignored by half the scanners:** `system-junk`, `browser-cache`, `app-leftovers`, and `registry` scanners use hardcoded/auto-detected locations and never read `this.config.paths`. A user who adds `D:\MyData` to scan paths will see it used by `big-files`, `duplicates`, `stale-files`, and `empty-items`, but the other four ignore it entirely. No UI indication of this.

### Capability 3: Scanner Events (Push)

- **Entry**: Worker `parentPort.postMessage({ type, data })`
- **Layers**: WorkerManager → `webContents.send(channel, data)` → preload `ipcRenderer.on(channel)` → renderer hooks → Zustand store
- **Destination**: `useScanStore` state updates → component re-renders

**Status: Happy-path event flow works correctly — field names, channel names, and data shapes align. Issues are in edge cases and error paths.**

**Gaps Found:**

| # | Where | What's Lost | Impact | Severity |
|---|-------|------------|--------|----------|
| 8 | `worker-manager.ts:120-129` | Force-terminated workers (cancel timeout) report as `error` not `cancelled` — UI shows confusing error instead of clean cancellation | Scanner stuck in `error` state with "Worker exited with code 1" message | **High** |
| 9 | `useScanner.ts:42-45` vs `:48` | `progress` handler missing `scannerType` field guard (unlike `result`/`error`/`cancelled` handlers) | Malformed progress event silently creates phantom store entry keyed on `undefined` | Medium |
| 10 | `main.tsx:40` + `useScanner.ts:39-71` | StrictMode double-invoke creates window where all scanner event listeners are unregistered | Events emitted during unmount-remount cycle are permanently lost; scan appears frozen | Medium |
| 11 | `ipc.ts:79-81` + `worker-manager.ts:113` | Cancel on non-running worker is silent no-op — renderer gets no feedback | If store is stuck in `scanning` state, cancel provides no recovery | Low |

**Details:**

**Gap 8 — Force cancellation misreported as error (HIGH):** When `cancelScan` is called and the worker doesn't respond cooperatively within 5 seconds, `worker.terminate()` is called (`worker-manager.ts:124`). The worker exits with non-zero code, triggering the `exit` handler (`worker-manager.ts:100-106`) which calls `callbacks.onError()`. The renderer receives a `scanner:error` event, not `scanner:cancelled`. The store status goes to `'error'` with the message `"Worker exited with code 1"` — confusing and wrong. `callbacks.onCancelled()` is never called on this path. Fix: in the force-terminate timeout, call `callbacks.onCancelled(scannerType)` explicitly before or instead of relying on the `exit` handler.

### Capability 4: Clean Flow

- **Entry**: User selects scan results → `useCleaner.requestClean()` → confirm dialog → `useCleaner.confirmClean(action, moveTo)`
- **Layers**: preload `startClean(items, action, moveTo)` → ipc.ts handler → `cleanItems()` in `src/main/cleaners/cleaner.ts`
- **Destination**: Items processed, progress events back to UI, `CleanResult` returned

**Gaps Found:**

| # | Where | What's Lost | Impact | Severity |
|---|-------|------------|--------|----------|
| 12 | `settings-store.ts:90` → `useCleaner.ts:55` | `quarantinePath` setting never pre-fills the move dialog; user must retype path each time | "Move to quarantine" setting is a no-op for the clean flow | Medium |
| 13 | `cleaner.ts:94-101` → `CleanProgress.tsx:52` | Progress events fire BEFORE item processing — `bytesRecovered`/`successCount` lag by one item | Mid-clean progress bar shows wrong byte count | Low |
| 14 | `scanners/registry/scanner.ts` → `cleaner.ts:105,109` | Registry key paths passed to `fs.stat`/`fs.rm`/`trashItem` — all filesystem operations | All registry item cleans fail with ENOENT; no registry-specific cleaner exists | **High** |
| 15 | `ConfirmDialog.tsx:109` → `ipc.ts:127` → `cleaner.ts` | No hard gate on red-risk items — warning shown but confirm button not disabled | Red-risk items cleaned with single click, no enforcement | Medium |

**Details:**

**Gap 14 — Registry cleaning is completely broken (HIGH):** The registry scanner produces `ScanResult` objects whose `path` is a Windows registry key path (e.g., `HKEY_CURRENT_USER\Software\...`). When the user selects these and clicks Clean, the cleaner calls `await stat(item.path)` on a registry key path — this is not a filesystem path. Every registry clean operation fails with `ENOENT`. There is no registry-specific cleaner module that uses the Windows Registry API. The error surfaces as a generic failure count with no explanation.

**Gap 12 — `quarantinePath` ignored:** The user can configure a quarantine folder path in Settings. When they choose "Move" in the clean confirm dialog, the move destination field starts empty — the stored `quarantinePath` is never read or pre-filled. The user must type the path manually each time.

### Capability 5: AI Advisory Flow

- **Entry**: AISettings (configure + test) and AdvisorPanel (configure + analyze)
- **Layers**: preload → ipc.ts → `advisor` singleton → AI provider classes → remote API
- **Destination**: AI advice displayed in AdvisorPanel; test results in AISettings

**Gaps Found:**

| # | Where | What's Lost | Impact | Severity |
|---|-------|------------|--------|----------|
| 16 | `secure-store.ts:69-72` → `AISettings.tsx:34` | `hasApiKey` checks JSON key presence, not whether decryption succeeds | UI shows "API key saved" when key is actually unreadable — AI calls fail with 401 | **High** |
| 17 | `App.tsx` / `SettingsView.tsx:14-36` → `AdvisorPanel.tsx:14-15` | Settings not hydrated until Settings tab is visited; AdvisorPanel renders with defaults | AI appears disabled on first Dashboard load even when configured | **High** |
| 18 | `ipc.ts:22-35` → `ollama.ts:25` | Non-localhost Ollama URL silently dropped by `validateLocalUrl`, falls back to `localhost:11434` | User-entered LAN Ollama URL ignored with no feedback | Medium |
| 19 | `ipc.ts:192-194` vs `advisor.ts:71-74` | `analyze`/`explainItem` throw raw exceptions; `testConnection` returns `{ok, error}` | Asymmetric error handling across AI operations | Low |

**Details:**

**Gap 16 — `hasApiKey` doesn't verify decryptability:** `hasApiKey` only checks if an entry exists in the `api-keys.enc` JSON map. It does not attempt `safeStorage.decryptString()`. If the encrypted blob is corrupted (OS reinstall, keychain reset), `hasApiKey` returns `true` while `getApiKey` silently returns `''`. The UI shows "API key saved (encrypted)" and the user has no indication the key needs to be re-entered. AI calls fail with auth errors.

**Gap 17 — Settings not loaded at app startup:** The Zustand settings store initializes with hardcoded defaults (`aiProvider: 'none'`, `aiEnabled: false`). The actual persisted settings are only loaded when `SettingsView` mounts (user visits the Settings tab). If the user goes straight to the Dashboard, `AdvisorPanel` reads `aiEnabled: false` and shows "AI features are disabled" — even though AI is fully configured on disk.

### Capability 6: Settings Lifecycle

- **Entry**: Settings UI components (General, Scan, AI)
- **Layers**: Zustand store → preload → ipc.ts → `store.ts` (JSON file) / `secure-store.ts` (encrypted)
- **Destination**: Persisted settings on disk, loaded on next session

**Gaps Found:**

| # | Where | What's Lost | Impact | Severity |
|---|-------|------------|--------|----------|
| 20 | `SettingsView.tsx:39-41` | `persist()` Promise not awaited or caught — save failures are invisible | Settings appear saved in-session but lost on next launch | **High** |
| 21 | `ipc.ts:163` → `store.ts:68` | No runtime validation on `settings:save` — bad types accepted and persisted | NaN→null, wrong enum strings survive to disk and break on reload | Medium |

**Details:**

**Gap 20 — Silent save failures:** `persist()` calls `window.electronAPI.saveSettings(partial)` but never awaits the Promise or attaches `.catch()`. If `writeFileSync` throws (disk full, permissions), the Zustand store has already been updated optimistically. The user sees their changes reflected immediately, but on next launch `loadSettings()` reads the stale file and the changes are gone. No error toast, no indication.

## Systemic Patterns

### Pattern 1: Settings Hydration Gap
Settings are only loaded from disk when the Settings tab is visited. Every other component (scanner, AI advisor, cleaner) that reads from the Zustand settings store during app startup gets hardcoded defaults instead of the user's persisted preferences. This affects:
- Scanner config (`scanPaths`, `exclusions`, `maxDepth`, etc.) — Gap 17
- AI config (`aiEnabled`, `aiProvider`) — Gap 17
- Clean defaults (`defaultCleanAction`, `quarantinePath`) — partially, Gap 12

**Root cause:** No app-level settings bootstrap in `App.tsx` or `main.tsx`. Fix once, fixes three capabilities.

### Pattern 2: Features Built Server-Side but Never Connected to UI
Multiple capabilities are fully implemented in the main process but have no renderer entry point:
- `aiExplainItem` — Gap 2
- `isAdmin` — Gap 3
- `reset`/`resetAll` store actions — Gap 23
- `setFocusedId` in preview — Gap 22

These aren't half-built — the backend code works. The UI wiring was simply never completed.

### Pattern 3: Config Fields That Silently Do Nothing
Several user-facing config options are collected, transmitted through IPC, and arrive at scanners — where they're ignored:
- `exclusions` — Gap 4 (Critical)
- `paths` for 4/8 scanners — Gap 7
- `maxSize`, `includeExtensions`, `excludeExtensions` — Gap 6
- `quarantinePath` for clean flow — Gap 12

The pattern is consistent: the type system and UI suggest the feature works, but the consuming code never reads the field.

### Pattern 4: Error/Edge-Case Paths Mishandled
Normal operation works; edge cases break silently:
- Force cancel → reports as error, not cancellation — Gap 8
- `hasApiKey` → checks existence, not decryptability — Gap 16
- Registry clean → filesystem ops on registry paths → ENOENT — Gap 14
- `persist()` → save failure invisible — Gap 20
